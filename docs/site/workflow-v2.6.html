Electronic Scoresheet Workflow v2.6

Development implementation — local workflow runtime, not Elsa.

Game lifecycle

  1. Rink scorekeeper ends the game and submits an unofficial scoresheet.
  2. The workflow records a hashed, immutable document revision as SUBMITTED.
  3. An assigned referee uses the mobile review page to approve and sign the exact digest, or request a correction.
  4. If corrected, the authoritative game journal receives a new audit event, the old revision is superseded, and a new one is submitted.
  5. Approval creates persistent delivery intents. An authorized operator invokes the development delivery worker after the league fixture is bound.
  6. A league result is published only when the fixture and permanent player attribution are valid. Opted-in parent notifications are queued after publication.

Operator commands

Start the local server with ICEBREAKER_LEAGUE_GAME_ID bound to a fixture. Use the existing referee review page for approval. With the operator credential, inspect GET /api/scoresheet/v1/workflow and invoke POST /api/scoresheet/v1/deliver.

Deliveries that cannot be processed remain visible as BLOCKED and are not treated as published. This milestone does not include a production background worker or real outgoing email.

Trust boundaries

Scoring remains rink-authoritative. Only a referee account assigned to the game can sign a digest. A workflow file cannot authenticate anyone or bypass journal and roster checks. Parent email preferences and youth privacy are checked before queueing.

Future Elsa integration

Elsa can eventually coordinate multi-official approval, deadlines, reminders, escalations, and exceptional league workflows. The authority, journal, digest, credentials, and certified-statistics constraints will remain separate. See requirements/workflow-runtime/v2.6.md.
