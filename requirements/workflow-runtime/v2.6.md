# IceBreaker v2.6 — executable scoresheet workflow and certified delivery

**Status:** Implemented development increment, not Elsa / not production deployment.

- **WF-026-001 (P0)** Workflow instances SHALL persist game ID, definition identifier, semantic version, content digest, current state and monotonic revision in SQLite.
- **WF-026-002 (P0)** A running game's workflow definition SHALL be pinned; different policy content or version on restart SHALL fail closed.
- **WF-026-003 (P0)** Submission, referee decision and correction SHALL use allowed role/state transitions from the pinned policy. The domain engine SHALL independently enforce authentication, no TBD, signed digest match and event integrity.
- **WF-026-004 (P0)** Referee approval SHALL atomically record the workflow transition, scoresheet certification and durable publication/notification intent, with idempotent event keys.
- **WF-026-005 (P0)** Correction requests, audited amendments and resubmissions SHALL advance distinct workflow states and reject stale revision signatures.
- **WF-026-006 (P0)** League publication SHALL only use a matching certified digest, a bound scheduled fixture, explicit permanent player identity resolution, a reconciled score and optimistic league-game versioning.
- **WF-026-007 (P0)** Public player statistics SHALL change only after successful certified league publication; failed mapping must not change standings.
- **WF-026-008 (P0)** Parent report emails SHALL be queued only for verified users with opt-in preferences and a favorite involved team, after league publication. Duplicate delivery attempts SHALL NOT create duplicate outbox entries.
- **WF-026-009 (P0)** Workflow actions, revision bound approvals, publication state and errors SHALL be accessible only to authorized operators/officials, not spectators.
- **WF-026-010 (P1)** Delivery failures SHALL remain visible and retriable using an authenticated recovery workflow; verified email transport must return an acknowledgment before marking an outbound email delivered.
- **WF-026-011 (P1)** Centralized workflow orchestration SHALL support Elsa or an equivalent maintained engine through an adapter, preserving security/transaction invariants in the game authority.
- **WF-026-012 (P1)** Certified revision replacement SHALL use a league-admin authorized amendment/recalculation process, never overwrite immutable results without audit.

## Acceptance checks

- Workflow configured transitions execute, persist, and reject invalid states.
- Server restart retains workflow state and previously queued deliveries without replaying approvals.
- Changed workflow definition during an active game is rejected.
- Postgame correction creates new signed revision; original digest/signature is invalid for the next revision.
- Bound certified game publishes official score and permanent-ID player statistics; unbound game blocks delivery visibly.
- Verified opted-in parent favorite causes one mail-outbox record with score/shots summary; repeated worker run creates no duplicate.
- Errors or conflicts do not mark league publication as delivered.

## Current limitations

- The embedded policy interpreter is intentionally small, synchronous, Node.js + SQLite and **not Elsa**. It does not handle timers, scheduled human tasks, visual designer or dynamic workflow migration.
- Publication and email notification jobs are currently invoked through a protected development endpoint. This is **not** the central remote-rink production pipeline.
- Email delivery remains queued in `parent_mail_outbox`; there is no configured SMTP/API email transport.
- When an already-certified league fixture receives an amended scoresheet, automated republication is deliberately blocked until an audited certified-revision update service is built.
- Game ID is still the local development game ID, bound to a league fixture by `ICEBREAKER_LEAGUE_GAME_ID`. Production game identity, roster confirmation and device assignment require integration.
- Workflow definitions must be code-reviewed and deployed securely; configuration files are not user-editable scripting and cannot bypass domain guards.
